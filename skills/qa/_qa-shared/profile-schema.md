# Project Profile Schema

The Project Profile is built automatically before every QA run. It determines which checks are active, adjusts severity thresholds, and maps features to reasoning patterns.

## Profile Structure

The profile has three layers:
1. **Stack Detection** (auto-detected from code) — saved to `.qa-profile.yaml`
2. **Feature Map** (dynamic, computed every run) — never saved, always fresh
3. **Gates** (derived from stack + context) — controls which checks run

---

## Layer 1: Stack Detection

Auto-detected from `package.json`, imports, and project structure. Saved to `.qa-profile.yaml` at project root.

### Schema

```yaml
project_profile:
  # Applications detected in the project
  apps:
    - path: string              # Relative path from project root
      type: string              # "patient-facing" | "admin-dashboard" | "mobile-wrapper" | "api-only"
      framework: string         # "react" | "vue" | "angular" | "svelte" | "next" | "nuxt" | "flutter"
      router: string            # "react-router-dom@6" | "vue-router@4" | "angular-router" | etc.
      state: string             # "redux-toolkit" | "zustand" | "pinia" | "vuex" | "ngrx" | "context-only"
      css: string               # "tailwind" | "css-modules" | "styled-components" | "scss" | "emotion"
      validation: string        # "zod" | "yup" | "joi" | "valibot" | "manual"
      form: string              # "react-hook-form" | "formik" | "vee-validate" | "angular-forms" | "native"
      data_fetching: string     # "tanstack-query" | "swr" | "rtk-query" | "apollo" | "manual"
      ui_library: string        # "shadcn" | "mui" | "antd" | "chakra" | "element-plus" | "vuetify" | "none"
      build: string             # "vite" | "webpack" | "next" | "nuxt" | "angular-cli"

  # Backend (if detected)
  backend:
    framework: string           # "nestjs" | "express" | "django" | "spring-boot" | "laravel" | "fastapi" | "go"
    orm: string                 # "typeorm" | "prisma" | "sequelize" | "mongoose" | "django-orm" | "sqlalchemy" | "drizzle" | "eloquent"
    auth: string                # "jwt" | "session" | "oauth2" | "firebase-auth" | "passport"
    validation: string          # "class-validator" | "joi" | "pydantic" | "spring-validation" | "laravel-validation"
    database: string            # "postgresql" | "mysql" | "mongodb" | "sqlite" | "mssql"
    cache: string               # "redis" | "memcached" | "none"
    realtime: string            # "socket.io" | "ws" | "sse" | "pusher" | "none"

  # Context (manually set or inferred from CLAUDE.md / README)
  context:
    language: string            # "ko" | "en" | "ja" | "zh" | "multi"
    target_users:
      primary_age: number       # Average age of primary users (affects UX thresholds)
      tech_proficiency: string  # "low" | "medium" | "high"
    domain: string              # "healthcare" | "fintech" | "ecommerce" | "education" | "saas" | "internal-tool"
    data_sensitivity: string    # "high" (PII/medical/financial) | "medium" | "low"
    deployment: string          # "web-only" | "webview-wrapped" | "native-mobile" | "desktop"
    platform: string[]          # ["web", "ios", "android", "ios-webview", "android-webview"]
    scale: string               # "small" (<1K users) | "medium" (1K-100K) | "large" (100K+)
    maturity: string            # "prototype" | "pre-release" | "production" | "legacy"
```

### Detection Procedure

1. Read `package.json` (or equivalent) in project root and each subdirectory
2. Match dependency names against the framework detection tables in `reference.md`
3. For context fields that cannot be auto-detected (language, domain, target_users):
   - Check `CLAUDE.md` for project description and user demographics
   - Check `README.md` for project overview
   - If not found, prompt user on first run and save to `.qa-profile.yaml`
4. Save detected stack to `.qa-profile.yaml`

### `.qa-profile.yaml` File

Only stack and context are persisted. Feature Map is always computed dynamically.

```yaml
# Auto-generated by qa-scan. Manual edits to context section are preserved.
project_profile:
  apps:
    - path: "frontend/"
      framework: "react"
      # ... (auto-detected)
  backend:
    framework: "nestjs"
    # ... (auto-detected)
  context:
    language: "ko"
    target_users:
      primary_age: 60
      tech_proficiency: "low"
    domain: "healthcare"
    data_sensitivity: "high"
    deployment: "webview-wrapped"
    platform: ["web", "ios-webview", "android-webview"]
    scale: "small"
    maturity: "pre-release"
```

## Layer 2: Feature Map (Dynamic)

Computed fresh on every QA run by scanning the codebase. Never persisted to disk.

### Feature Categories

#### `crud_list_detail` — List + Detail page patterns
**Scan procedure:**
1. Find all page/view files (using Page File Patterns from reference.md)
2. For each page, check if it renders a table/list component
3. Find corresponding detail pages (same module, `:id` param in route)
4. Match to backend entities via API service calls

```yaml
crud_list_detail:
  - entity: string          # Entity name (from backend module or API path)
    list: string            # Frontend route path
    detail: string          # Frontend route path with param
    list_api: string        # Backend endpoint for list
    detail_api: string      # Backend endpoint for detail
    has_count_columns: boolean  # Whether list displays aggregated counts
```

#### `realtime` — WebSocket / Server-Sent Events
**Scan procedure:**
1. Grep for socket.io, ws, EventSource, SSE imports
2. Find gateway/handler files
3. Extract event names and namespaces

```yaml
realtime:
  - type: string            # "socket.io" | "ws" | "sse" | "pusher"
    namespace: string       # Socket namespace (if applicable)
    events: string[]        # Event names
    entities: string[]      # Entities affected by real-time updates
```

#### `role_views` — Same feature with different role-based views
**Scan procedure:**
1. Find features that exist in multiple apps (frontend/, frontend-dashboard/, mobile/)
2. Find route guards or role checks
3. Map features to roles

```yaml
role_views:
  - feature: string         # Feature name
    roles: string[]         # Roles that have access
    apps: string[]          # Which apps implement this feature
```

#### `aggregations` — Displayed counts, sums, averages
**Scan procedure:**
1. Grep for `Count`, `count`, `total`, `length` in list/table column definitions
2. Trace the data source (API response field → backend calculation)
3. Find the detail view that shows individual items

```yaml
aggregations:
  - display: string         # Where the count is displayed (page + component)
    field: string           # Field name (e.g., "patientCount")
    source_entity: string   # Which entity/table is being counted
    source_query: string    # Backend method that calculates the count
    detail_query: string    # Backend method that fetches the actual items
```

#### `soft_delete_entities` — Entities with soft delete
**Scan procedure:**
1. Find entities extending BaseEntity or having `deletedAt` column
2. List all repository methods that query these entities

```yaml
soft_delete_entities:
  - entity: string          # Entity name
    table: string           # Database table name
    queries: string[]       # Repository methods that touch this table
```

#### `state_machines` — Entities with state/status fields
**Scan procedure:**
1. Find enum columns or string columns with constrained values
2. Extract possible values from enum definition, migration, or constants

```yaml
state_machines:
  - entity: string          # Entity name
    field: string           # Column name (e.g., "status")
    values: string[]        # All possible values
    transitions: object[]   # Known transition rules (if defined)
```

#### `file_uploads` — File upload endpoints
**Scan procedure:**
1. Grep for multer, upload, multipart, @UseInterceptors(FileInterceptor)
2. Find the endpoint and accepted file types

```yaml
file_uploads:
  - endpoint: string        # API endpoint
    type: string            # "image" | "video" | "document" | "any"
    max_size: string        # If configured
    storage: string         # "s3" | "local" | "cloudinary"
```

#### `scheduled_tasks` — Cron jobs, background tasks
**Scan procedure:**
1. Grep for @Cron, celery, bull, agenda, node-cron
2. Find task handlers and their schedules

```yaml
scheduled_tasks:
  - name: string            # Task name
    schedule: string        # Cron expression or interval
    entities: string[]      # Entities affected
```

## Layer 3: Gates (Derived)

Gates are boolean flags derived from the stack and context. Each Tier 1 check references a gate to determine if it should run.

### Gate Derivation Rules

```yaml
gates:
  # ── Context / UX ──
  cjk_ime: context.language in ["ko", "ja", "zh"]
  elderly_ux: context.target_users.primary_age >= 55
  i18n_multi_locale: context.language == "multi"
  high_data_sensitivity: context.data_sensitivity == "high"
  large_scale: context.scale == "large"
  production_maturity: context.maturity == "production"

  # ── Platform ──
  webview_checks: context.deployment == "webview-wrapped"
  has_native_wrapper: apps contains type "mobile-wrapper"
  is_mobile_target: any platform contains "mobile" or "webview" or "android" or "ios"
  safe_area: any platform contains "webview" or "ios" or "android"
  mobile_keyboard: any platform contains "mobile" or "webview"
  platform_ios: any platform contains "ios" or "ios-webview"
  platform_android: any platform contains "android" or "android-webview"

  # ── Backend ──
  has_backend: backend.framework is not null
  backend_nestjs: backend.framework == "nestjs"
  backend_django: backend.framework == "django"
  backend_node: backend.framework in ["nestjs", "express"]

  # ── Frontend ──
  has_frontend: apps contains framework in ["react", "vue", "angular", "svelte", "next", "nuxt"]
  frontend_spa: apps contains router != null

  # ── Data ──
  has_orm: backend.orm is not null
  has_realtime: backend.realtime != "none"
  has_auth: backend.auth is not null
```

### How Gates Work in Practice

Every Tier 1 check has an optional `gate` field:

```markdown
| # | Check | Severity | Gate | Description |
```

- If `gate` is empty or "always": check always runs
- If `gate` is specified: check runs only when gate is `true`
- Gates can also adjust **parameters** (not just skip/include):

```
Check: "Touch target too small"
  gate: always (runs for all projects)
  threshold: gates.elderly_ux ? 48px : 44px

Check: "WebView back button deduplication"
  gate: gates.has_native_wrapper (skipped for pure web apps)

Check: "IME composition guard on search input"
  gate: gates.cjk_ime (skipped for English-only projects)

Check: "Missing viewport-fit=cover"
  gate: gates.webview_checks (skipped for pure web apps)

Check: "Fixed bottom element missing safe-area padding"
  gate: gates.safe_area (skipped for desktop-only web apps)

Check: "iOS input auto-zoom"
  gate: gates.platform_ios (skipped for Android-only or web-only)

Check: "Static route shadowed by parameterized route"
  gate: gates.backend_nestjs (NestJS decorator routing specific)

Check: "inputmode attribute missing"
  gate: gates.is_mobile_target (skipped for desktop-only web apps)

Check: "Name field character restriction regex"
  gate: always
  pattern:
    cjk_ime ? /^[가-힣ぁ-んァ-ヶ一-龥a-zA-Z\s]+$/ : /^[\p{L}\s'-]+$/u
```

## Feature → Reasoning Pattern Mapping

After Feature Map is computed, qa-scan automatically maps features to applicable Reasoning Patterns:

| Feature Category | Reasoning Patterns Applied |
|-----------------|---------------------------|
| `crud_list_detail` | RP-01 (Data Flow), RP-03 (Filter Consistency), RP-07 (Aggregation Parity) |
| `realtime` | RP-09 (Concurrency & Race) |
| `role_views` | RP-05 (Permission Boundary), RP-11 (Cross-App Consistency) |
| `aggregations` | RP-07 (Aggregation Parity) — highest priority |
| `soft_delete_entities` | RP-03 (Filter Consistency), RP-12 (Soft Delete Ripple) |
| `state_machines` | RP-02 (State Lifecycle) |
| `file_uploads` | RP-10 (Error Path Completeness) |
| `scheduled_tasks` | RP-06 (Temporal Consistency), RP-09 (Concurrency) |

This mapping ensures reasoning patterns are targeted to features where they are most likely to find issues, rather than applied blindly across the entire project.

---

## Profile Lifecycle

1. **First run**: Auto-detect stack → prompt user for context fields → save `.qa-profile.yaml`
2. **Subsequent runs**: Load `.qa-profile.yaml` → re-detect stack (update if changed) → preserve manual context fields → compute Feature Map fresh
3. **Manual override**: User can edit `.qa-profile.yaml` context section directly
4. **Force re-detect**: `qa-scan --redetect` ignores saved profile and re-detects everything
